# ETF Flow Radar 系统体检（2026-08-17）

## 结论

本次体检发现并修复了多处会影响资金流可信度的高优先级问题。最重要的结论是：**2026-08-14 按本项目目标口径（A股股票ETF、日终份额变化估算一级市场净申赎、公司行动调整后）并不是净流入200多亿元，而是净流出约48亿元。**

独立复核脚本不读取当前 `latest.json`，而是从修复前归档的交易所ETF日终份额重新构造 T/T-1 样本，再使用精确交易日的独立基金类型/NAV面板进行估值和公司行动确认。复核结果：

- 交易所ETF：2026-08-14 共 1605 只，前一日 1604 只，T/T-1 匹配 1604 只。
- 全部“股票型ETF”（含跨境等）：1489 只，成交均价口径估算净流出 **58.48亿元**。
- 本项目目标“A股股票ETF”范围：1247 只，成交均价口径估算净流出 **47.80亿元**；NAV口径净流出 **48.30亿元**。
- 已归类的A股股票ETF：1211 只，估算净流出 **47.63亿元**。
- 36只尚未归类但属于A股股票ETF的产品合计仅约 **-0.17亿元**，因此分类缺口不是“46亿 vs 200亿”的来源。
- 588710 科创半导体设备ETF华泰柏瑞确认发生 1:3 份额单位调整：份额从 3,592,295,000 变为 10,656,885,000，单位净值从 3.1344 降至 1.0532。将历史份额调整到同一单位后，当日估算净申赎约 **-1.26亿元**；若不做公司行动调整，会错误得到约 **+74.40亿元（NAV估值）** 的伪流入。

随后用修复后的生产逻辑做过一次完整历史回放，得到 A股股票ETF市场范围 1249 只、当日净流出 **48.23亿元**，588710 为 **-1.26亿元**。1247/1249 与 -47.80/-48.23 的小差异来自精确交易日第三方基金类型/名称面板在不同抓取时点的边界记录变化；核心方向和量级一致。生产系统已经把“市场范围”和“已归类范围”拆开记录并对账。

## 已发现并修复的严重问题

### P0：第三方份额覆盖交易所官方份额

旧逻辑在“交易所份额出现大跳变，而第三方最新份额仍接近前一日”时，会把交易所官方值替换成第三方值。这个判断把“第三方滞后”错误当成“交易所异常”，直接导致588710的官方1:3份额调整被抹掉。

修复：**沪深交易所日终份额永远是主源。第三方最新份额只做交叉核验，不能覆盖官方值。** 差异被记录为审计事件，随后进入公司行动识别。

### P0：公司行动识别依赖未调整交易价格

旧公司行动识别主要依赖历史收盘价反向跳变。拆分当日行情源可能滞后、未调整或出现复权口径差异，不能作为唯一确认条件。

修复：先检测份额是否接近 2、3、4、5、1/2、1/3 等合理比例，再使用**精确交易日单位净值的反向比例变化**确认；只有精确NAV不可用时才回退历史价格确认。

### P0/P1：SSE接口份额单位可能发生表示变化

历史接口/文档曾以“万份”表示份额，而较新的AKShare接口可能直接返回“份”。若永久假设某一种单位，存在全市场 10,000 倍错误风险。

修复：SSE适配层新增横截面单位审计，使用全市场份额分布的稳健分位数识别旧“万份”表示并只放大一次；若归一化后数量级仍不合理，任务直接失败，不允许发布。

### P1：全市场总量错误依赖分类成功

旧 `market.flow1d` 来自 `valid`（已分类 + 历史完整 + 有价格）ETF。这样新上市、尚未归类但确实属于A股股票ETF的产品会从“全市场”总量里消失。

修复：市场总量独立计算。先按精确交易日基金类型识别股票型ETF，再剔除跨境、债券、商品、货币等非A股股票品种；**市场总量不依赖分类是否成功**。分类只影响宽基/风格/行业/主题分组。

### P1：热门主题被误称为申万一级行业

旧分组结构把“半导体、芯片、券商”等叶子组直接放在 `kind=industry` 下，前端结论又把所有 `kind=industry` 称为“申万一级行业”，因此可能出现“申万一级行业流出最多的是半导体”这种语义错误；同时电子一级行业没有把半导体/芯片等子主题完整回卷。

修复：保留每只ETF唯一叶子归属以避免重复计算，同时新增 `industryRollups`：把热门主题按 `parent` 回卷到 SW2021 一级行业。结论的“申万一级行业”只使用父级汇总；热门主题单独展示。

### P1：5日/20日被错误描述为“累计资金流”

现有代码的 5日/20日算法是：期末份额减去 5/20 个交易日前份额，再乘**期末参考价**。这属于“端点份额变化估算”，不是逐日资金流求和。

修复：方法说明和构建后的页面统一改为“5日/20日端点资金变化/端点份额变化估算”，禁止再称为“累计净流入”。未来若要真正累计资金流，应保存每日可比参考价并计算 `sum(delta_shares_t * price_t)`。

## 自动更新与效率

### 已修复

- 每日生产入口统一为 `data_pipeline/update_daily_production.py`，文档不再错误地让人工从基础入口绕过保护层。
- 自动任务从每天7次（00:15、00:30、01:00、05:00、06:00、07:00、08:00）精简为北京时间 **05:00、06:00、07:00、08:00** 四次。
- `concurrency.cancel-in-progress` 改为 `true`，避免慢任务和下一次定时任务叠加。
- GitHub Pages 删除 `workflow_run` 的重复部署触发，仅保留 `main` push；数据机器人提交后只部署一次。
- 同一交易日已经发布时，基础入口会直接退出，不会重复重跑完整21日窗口。

### 当前仍存在的可用性风险

GitHub Hosted Runner 对上交所数据源存在偶发 403 / JSON空响应。系统当前采用“AKShare维护接口优先 + 旧官方接口回退”，两者都不可用时 **fail closed**，保留上一份已验证快照。这比发布错误数据安全，但意味着极端情况下自动更新会延迟。

### 下一阶段更高效的架构

当前新交易日仍需重新抓取约21个历史交易日份额，并为大量分组读取收益代理，调用链偏重。更优方案是：

1. 每日只采集并落盘 T 日原始数据（交易所份额、NAV、成交均价、基金类型、公司行动标志）。
2. 建立不可变的 `raw/YYYY-MM-DD` 标准化缓存；历史日不重复联网抓取。
3. 从本地21日缓存计算1/5/20日和行业/主题汇总。
4. 保存每日单ETF `flow1d`，5/20日改成真正逐日求和。
5. 对缺失的收益代理做独立缓存，不在每次资金任务中重新抓取全部历史价格。

这样可以明显缩短GitHub Actions运行时间、降低接口限流概率，也能把资金口径从“端点估算”升级为真正的多日累计。

## 不应混用的“ETF资金流”口径

本项目目标是一级市场申购赎回代理：**日终份额变化 × 可比参考价格**。财经终端/资讯中另有“主力净流入、两市ETF资金流入/流出”等二级市场交易资金指标，它们来自成交/主动买卖拆分，与ETF份额申赎不是同一变量，同一天可以一正一负。系统今后不应拿二级市场“主力资金流”去校准一级市场申购赎回估算。
